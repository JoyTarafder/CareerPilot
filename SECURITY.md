# CareerPilot — Security Architecture & Controls

## 1. Security position

No internet-facing system can be guaranteed “unhackable.” The goal is defense in depth: prevent common attacks, reduce blast radius, detect abuse quickly, and recover safely. CareerPilot handles identity, employment history, contact details, and uploaded documents; treat this data as sensitive.

## 2. Security principles

- Deny by default; least privilege for users, admins, services, and database roles.
- Server is authoritative; frontend checks are UX only.
- Validate at every trust boundary and encode for the output context.
- Minimize collected data, retention, logs, and third-party exposure.
- Use established libraries; never implement cryptography manually.
- Separate authentication, authorization, ownership, and auditing.
- Fail closed without leaking secrets or internals.

## 3. Threat model summary

| Threat | Primary controls |
|---|---|
| Credential stuffing/brute force | Rate limits, progressive delay, breached-password check, MFA for admins, alerts |
| Password database leak | Argon2id + unique salt + server pepper, secret rotation plan |
| Token theft/replay | Secure HttpOnly cookies, short access TTL, refresh rotation, reuse detection, session revocation |
| IDOR/BOLA | Ownership filter in every repository query, policy tests, opaque UUIDs (not a control alone) |
| XSS | React escaping, sanitization only where rich HTML is allowed, CSP, no unsafe script execution |
| CSRF | SameSite cookies + origin checks + CSRF token for state-changing cookie-auth requests |
| SQL injection | Prisma parameterization, no interpolated raw SQL, query allowlists |
| Prompt injection | Treat CV/JD as data, structured prompts, delimiter isolation, schema validation, no tool authority |
| Malicious uploads | Type sniffing, size/page limits, safe parsers, malware scan, isolated conversion, private storage |
| SSRF | Do not fetch arbitrary job URLs in MVP; later use URL validation, DNS/IP checks, egress proxy |
| Admin abuse | MFA, scoped permissions, no impersonation, support access workflow, immutable audit trail |
| Resource exhaustion | Body/file/token limits, rate limits, queue quotas, timeouts, concurrency controls |
| Supply-chain compromise | Lockfiles, dependency/SAST/secret scans, signed/provenance-aware builds, patch process |

## 4. Password security

### Candidate policy

The requested product limit is **12–30 characters**. Do not silently truncate. Count Unicode code points for UX and reject excessively large byte input before hashing. Permit spaces, paste, and password managers; do not require arbitrary symbol/uppercase recipes. Screen against common and known-compromised passwords.

Security note: a 30-character maximum limits long passphrases. If compatibility permits, increase to at least 64 characters before production.

### Hashing

Use Argon2id via a maintained library:

- Unique random salt generated by the library for every password.
- Server-side pepper loaded from a secret manager/environment and never stored in PostgreSQL.
- Parameters benchmarked on production-class hardware, targeting roughly 250–500 ms while respecting memory limits.
- Store algorithm/version/parameters in the encoded hash for future rehash.
- Compare in constant-time through the library.
- Rehash after successful login when parameters change.

Conceptual input:

```text
Argon2id(password bytes + versioned pepper, unique random salt)
```

Do not log password length/value, pepper, hash, reset token, or validation body.

### Admin bootstrap

```env
ADMIN_BOOTSTRAP_EMAIL="admin@example.com"
ADMIN_BOOTSTRAP_PASSWORD="high-entropy-one-time-secret"
PASSWORD_PEPPER_V1="secret-manager-reference"
```

- Only an explicit CLI/bootstrap job may read bootstrap credentials.
- Validate email and password; create the first admin idempotently; hash immediately.
- Never compare a login request directly to the environment password.
- Force production admin to change the bootstrap password and enroll MFA.
- Remove/rotate the bootstrap password after provisioning.
- Never expose secret variables to frontend builds, logs, CI artifacts, or `NEXT_PUBLIC_*`.

## 5. JWT and session design

- Access JWT lifetime: 5–10 minutes.
- Sign with asymmetric keys (`EdDSA`/`ES256`/`RS256`) where operationally supported; API verifies `iss`, `aud`, `exp`, `nbf`, algorithm, key ID, and subject.
- Minimal claims: subject, session ID, role/scopes, issued/expiry; no CV or sensitive profile data.
- Refresh token: high-entropy opaque token, 7–30 day policy, stored in `Secure`, `HttpOnly`, `SameSite=Lax/Strict` cookie.
- Store only refresh-token hash and token-family metadata in DB.
- Rotate on every refresh. Reuse of an old token revokes the entire family and raises a security event.
- Revoke on logout, password change, suspension, suspicious reuse, and admin action.
- Separate candidate/admin audiences and cookie names. Admin sessions are shorter and require MFA/step-up for sensitive actions.
- Never put bearer tokens in `localStorage`.

If frontend and API are cross-site, review cookie/SameSite/CSRF behavior carefully; prefer same-site custom domains.

## 6. Authentication abuse controls

- Per-IP and per-account rate limits; stricter limits for login, reset, verification, AI, and export endpoints.
- Progressive backoff; avoid permanent lockout DoS.
- Generic login/reset responses to limit account enumeration.
- Single-use hashed reset/verification tokens with short expiration.
- Notify users of password change, new significant login, and session revocation.
- CAPTCHA/challenge only after risk signals, not for every user.
- Mandatory TOTP/WebAuthn-capable MFA for admins; recovery codes stored hashed.

## 7. Authorization

- Middleware authenticates; policy layer checks role/scope; repository query enforces ownership.
- Never load by record ID alone for candidate data. Pattern:

```ts
prisma.resume.findFirst({
  where: { id: resumeId, userId: auth.userId, deletedAt: null }
});
```

- Admin access is permission-based (`users.read_metadata`, `users.suspend`, `templates.write`, `support.read_sensitive`) rather than one unlimited boolean.
- Sensitive support access requires reason, time limit, approval where feasible, and audit event.
- Test horizontal and vertical privilege escalation automatically.

## 8. Input validation, sanitization, and output safety

- Validate every body, query, path, header, webhook, file metadata, and AI response with Zod/JSON Schema.
- Reject unknown fields on sensitive DTOs to prevent mass assignment.
- Set strict limits for JSON body, text, arrays, nesting, job-description length, AI tokens, and exports.
- Normalize email/domain fields carefully; do not globally mutate user prose.
- “Sanitization” is context-specific:
  - HTML: avoid raw HTML; if necessary, allowlist with a maintained sanitizer.
  - SQL: Prisma parameterization; never concatenate.
  - URLs: parse, allow `https`, reject credentials and private/internal targets before any server fetch.
  - Filenames: generate server-side object keys; original name is metadata only.
  - Logs: structured redaction and newline/control-character handling.
- Use output encoding appropriate to HTML, attributes, URLs, CSV, and document formats.

## 9. Browser and API defenses

Recommended headers:

- Strict Content Security Policy with nonces/hashes; no `unsafe-eval`.
- `Strict-Transport-Security` after HTTPS is stable.
- `X-Content-Type-Options: nosniff`.
- `Referrer-Policy: strict-origin-when-cross-origin` or stricter.
- `Permissions-Policy` disabling unnecessary browser capabilities.
- `frame-ancestors 'none'` (or approved origins) to prevent clickjacking.
- Correct restrictive CORS allowlist; never reflect arbitrary origins with credentials.

Also:

- Origin/Referer verification and CSRF token for state changes under cookie authentication.
- TLS everywhere; redirect HTTP to HTTPS.
- Do not expose stack traces, Prisma errors, provider messages, or environment details.

## 10. File-upload and document security

- Allow only necessary PDF/DOCX types; verify extension, declared MIME, and magic bytes.
- Enforce size, page, decompression, XML relationship, and processing-time limits.
- Store uploads in private object storage with random keys and no execute permission.
- Quarantine → scan → accept/reject state; use malware scanning where infrastructure supports it.
- Parse in an isolated worker/container with low privileges, read-only filesystem, memory/CPU timeout, and blocked outbound network.
- DOCX is a ZIP/XML container: defend against zip bombs, external relationships, macros, and path traversal.
- PDF renderer must not fetch arbitrary remote resources; allowlist/embed assets and use a fresh incognito context per job.
- Serve downloads with safe content type/disposition and short-lived signed URLs.
- Delete temporary files reliably and log only object IDs.

## 11. AI security and privacy

- Redact name, email, phone, exact address, IDs, and private links before Gemini free-tier requests.
- Obtain clear user consent and publish retention/provider disclosures.
- Treat CV and job text as untrusted data. Prompts must state that embedded instructions are content, not authority.
- Request JSON schema-constrained outputs; validate types, lengths, enums, and evidence references.
- The model cannot calculate the official score, access database tools, change permissions, or trigger admin actions.
- Deterministic scorer receives normalized facts only and records its rule version.
- Detect/limit prompt-injection patterns, but do not rely on detection alone.
- Minimize prompt logging; use redacted hashes/IDs for diagnostics.
- Set provider timeouts, token budgets, concurrency limits, and circuit breaker behavior.
- Show AI-generated status and require approval before changing a CV.

## 12. Database and secret security

- Managed PostgreSQL with encrypted transport and storage.
- Separate migration, application, read-only analytics, and backup identities.
- Application DB user has only required schema privileges; no superuser.
- Network-restrict database to backend/worker; no public access where avoidable.
- Encrypted backups, point-in-time recovery if available, periodic restore drills.
- Secrets live in a secret manager/platform environment—not Git, Docker images, frontend, or database.
- Rotate JWT signing keys, peppers, provider keys, DB credentials, and storage keys using documented procedures.
- Pepper rotation uses versioned peppers and rehash-on-login; emergency rotation includes forced resets where necessary.

## 13. Logging, audit, detection, and privacy

- Application logs exclude passwords, tokens, cookies, auth headers, raw CV/JD, uploaded files, and AI prompts.
- Immutable/append-only audit events for admin login, MFA changes, suspension, support access, scoring-rule changes, template publishing, and secret/security configuration events.
- Audit fields: actor, action, target type/ID, timestamp, request ID, IP/risk metadata, reason, before/after metadata—not secret content.
- Alert on refresh-token reuse, admin brute force, privilege changes, bulk access, abnormal exports, queue abuse, and repeated upload failures.
- Define data retention and deletion SLA. Cascade/anonymize derived data and delete objects from storage/backups according to policy.

## 14. Secure SDLC and verification

Required pipeline gates:

- TypeScript strict mode, lint, tests.
- Dependency and license scanning.
- Secret scanning and pre-commit protection.
- SAST and infrastructure/config checks.
- Prisma migration review.
- Unit tests for scoring and authorization policies.
- Integration tests against PostgreSQL.
- End-to-end authentication/session/CSRF tests.
- File-upload fuzz/negative tests.
- DAST in staging and independent penetration test before handling production CVs at scale.

Security acceptance checklist:

- [ ] No secret or token in frontend bundle, logs, URLs, or repository history.
- [ ] Passwords use Argon2id + unique salt + versioned pepper.
- [ ] Refresh rotation and replay detection verified.
- [ ] All candidate record queries enforce owner ID.
- [ ] Admin MFA, scoped permissions, and audit trail verified.
- [ ] Zod rejects unknown/oversized inputs and invalid AI output.
- [ ] CSRF, CORS, CSP, security headers, and cookie attributes tested.
- [ ] Upload isolation and resource limits tested with malicious fixtures.
- [ ] Backups restore successfully and incident runbook is exercised.

## 15. Incident response

1. Triage and classify severity.
2. Contain: revoke sessions/keys, disable affected feature, isolate worker/account.
3. Preserve redacted evidence and audit trail.
4. Eradicate root cause and patch with tests.
5. Recover from verified state and monitor closely.
6. Notify affected users/regulators according to applicable policy/law.
7. Complete blameless post-incident review with owned corrective actions.
